## 475 · A plan mode the harness restarts held an approved plan with no way out, and an end of plan mode the session did not call was recorded as an approval

**Enforced by:** GATE hub:plan-guard.mjs — the approval call passes for an approved plan, after a restart put the harness back in plan mode, when the newest owner-typed message ends with a go-word and was recorded after that plan mode began
**Enforced by:** GATE hub:approved-plan-guard.mjs — an accepted exit keeps a standing marker whose hash matches the plan file, and an end of plan mode the session did not call writes no marker under any mode
**Enforced by:** GATE hub:session-guards.test.mjs — each of the three has a case and a plant

**Recorded 2026-11-07.** Measured on 5, 6 and 7 November, California time, in one session, from the manager's notes and its transcript read in place.

**What happened.** The exit tests of the three days answered what the lesson before this one left open. On 5 November the owner's go arrived recorded under auto and ended plan mode from the app, no exit call was made by the session, and the dispatcher recorded that end as the approval; the session was never out of auto mode, so the test of an exit call under another mode did not run. Later that evening an exit call was made with the owner's newest message recorded under plan mode, it came back accepted in about ten seconds, and the owner's next message arrived under auto eighteen seconds later naming the tier to execute on, which fits the approval button that also enters auto mode. The second exit, on 6 November, came back the same way. So under plan mode the exit call on a go gives the button on this harness, and the two ends of 5 November that showed no button went up with the base mode auto.

Then the lock of 6 November. A compaction at 09:07 brought the harness back in plan mode with the plan already approved. The plan guard refused the exit call as a plan already approved, with no latch, and said to send the next step. That mode reaches every agent the session sends, and an agent in plan mode can write nothing, so the refusal and the mode left no route: the one step sent ended REFUSED after its first call, and the plan stood approved and unfinished until the owner replaced it with a new plan in the same file. The exit call of the new plan, made on 7 November in a plan mode the session entered on a go, came back approved and gave the button as the two before it had.

A call outside the plan's Commands and the fence's list also showed its cost on 5 November: it goes to the owner as a permission prompt and halts the run, and one such call at 22:49 cost a prompt, a worker restart and the hours between.

**What was wrong.** The refusal of an exit for an approved plan was written for a plan nothing had disturbed, and it was the only way out of a plan mode the harness itself restarts, so a gate built to prevent a second approval made the first one unusable. The approval guard wrote a marker from any end of plan mode it did not see the session call, under a mode the record could not tell from the owner's press, and it wrote a second marker over a standing one that still matched the file.

**The test.** After a restart the exit call passes when the newest owner-typed message ends with a go-word and was recorded after the harness's plan mode began, with a line saying the exit goes up on the owner's go so that the button stays the owner's; the checks of the plan's shape and of the talk are not run again, because the plan passed them at its approval and is unchanged. An accepted exit while a marker already stands whose hash matches the plan file keeps that marker and writes no second one. An end of plan mode the session did not call writes no marker under any mode, and the print says it is not the owner's approval. Each refusal and each pass sets no latch, because the owner's next message answers it.

**The general form.** A gate that refuses to repeat an act must leave the one door the environment itself closes behind a restart, or the gate and the environment wait on each other. And an approval is recorded from the call that asks for it, never from a state that merely follows it.

**What stays open.** The approval button that also enters auto mode leaves the session in auto, so the next plan's exit still waits on a change of mode by the owner. Whether a button appears on the owner's side is the owner's to say; the record shows only the call, its result and the next message's mode.
