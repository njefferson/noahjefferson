**What is done now.** Seven changes in the hub's guards and the texts that describe them, each with a case in the guards' test shown to fail against the old guards and pass against the new, and plants that take each part out.
- The check. `plan-guard.mjs --check` runs every check of the approval call on a plan file in one run and prints every fault in the refusal's own words. It records no refused name, and it says what it did not judge: the talk before the plan, which needs a turn of chat written after the plan's last edit, and, in a shell with no session, the Shipped check and the Asked test. The manager fence passes it for a file of the record as it passes the status command, in plan mode too, with nothing chained to it, and the reads gate counts it as no send. Rule 4 of the doctrine says it runs green before the talk turn.
- No latch for the plan's shape. A refusal at the approval call for a section that is missing, short or wrongly shaped sets no latch and its text names the check mode: the five sections of section 11f, the goals and their Served by line, Asked, the Order, Standing and After lines, the Rules, Roadmap and Shipped check sections. The talk, the name check and the held names keep their marks, and the talk still latches.
- The shapes in the doctrine. Rule 2 gains a paragraph on the Roadmap section, one bullet to an open item with its key, in or out, and why, and one on the Shipped check, a line to every item marked in, so the main thread writes the plan from the doctrine and does not find the shape at the button.
- The manager's notes. In plan mode a Write or Edit of status/manager.txt in the session scratchpad passes beside the plan file, and nothing else joins the list.
- The finished plan. `restartedPlanMode` answers nothing once every step in the Order of the marker's plan has a hand-back opening DONE, so a plan mode that comes on after it is not the plan's and the next plan's write passes; a plan with a step left, a FAILED or REFUSED hand-back or no Order keeps the gate.
- The reply guard. Its refusal of the main thread's Read of a file of the record sets no latch, since the reads gate already holds every send until that file is read; its refusal of any other call keeps the latch, and the text says which.
- The rules version. A change to the agent rules file lands only when no plan is in force, as the last step of the plan that makes it, and no plan is moved to a new rules version without the button. The Rules line has been part of the approved scope since lesson 433, so an amendment cannot carry a new version, and a send refused for a stale version is answered by a new plan through plan mode. The sentence that said to amend the Rules line is replaced in rule 13 and rule 14, in the header of hook-dispatch.mjs, in the rules-pin refusal and in the rules file's header, whose version is raised to 2 and reaches the live gate copy by the pull in the landing step. Rule 14's list of refusals that set no latch is rewritten from the code and counts nineteen, and the calls a latch passes are five.

**The excuse is that each refusal was right.** Each one named a real fault. What was wrong was the latch behind it, which was written for the case where a refusal means the session has gone somewhere it should not, and a missing section means nothing of the kind. A refusal whose remedy is a write of a file the session may write has to leave that write open, as lesson 424 says of a refusal whose remedy is a read. And a check that runs only at the approval call finds faults one at a time, because the place it runs is the place where a failure costs a message.

**What the changes cannot see.** The check judges the plan's sections and not its commands: a node line on a worktree file that the app's harness guard refuses is found by the review and not by the check (Found 0.24). It does not judge the talk, which can only come after a plan that is right, so the order of check and talk is a checklist item. Plan mode's own list of readers passes any node line whose words carry the --check flag, whatever file it runs (Found 0.25). The reply guard records a check that exits 1 as a failed call keyed by its text, so the same command line run again after the plan was edited is refused as a repeat of a failed call. Section 11f of the doctrine, on what the plan guard enforces, does not yet mention the check mode or the absence of a latch; rule 4 and rule 14 do.

**The general form.** A gate that finds faults has to find them all in one pass, before the step whose cost depends on them, and a refusal whose remedy is a write the session may make has no business latching.
