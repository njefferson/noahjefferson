## 415 · The rules-first refusal latched an agent at its very first call, so the first such refusal now sets no latch and says what to do, and a second one latches as every refusal does

**Enforced by:** GATE hub:session-guards.test.mjs — the case for the rules read first (the first refusal of an agent for its first call carries the mark `RULES FIRST, NO LATCH:`, sets no latch and says the next call is the Read of the rules; the second refusal does not carry the mark and latches; the Read of the rules after the first refusal passes) and the case for the approved plan read before the rules, each with plants that take out the mark, make every refusal a first one, and remove the skip in `hook-dispatch.mjs`, and each plant must fail its case

**Recorded 2026-10-20.** Lesson 404 made an agent's first call the Read of the shared rules, and lesson 410 let the plan and its steps file go first. The fence still refused every other first call with the same latching refusal as any other gate, so an agent sent a step that began with its own command, or with a read of a file other than the rules, was latched at that call. A latched agent can write its own report and hand back, and nothing else. An agent that had been told the rules were its first call had no way to learn that from the refusal, because the refusal did not say that the next call was the Read; it said only that a refusal had happened and the route was closed.

**What is done now.** `rulesFirst` in `plan-fence.mjs` gives the agent's first refusal for that check the text head `RULES FIRST, NO LATCH:` (`FIRST_REFUSAL`), and ends it by saying that the refusal sets no latch and is not the refusal the rules' line on refusals means, that its next call is the Read of the rules file, and that it then does its step with every file read through the Read or Grep tool. "First" is read from the agent's own transcript: no earlier error result of its transcript names the rules-first refusal (`rulesRefusedBefore`). Any later refusal of that check keeps the old text and latches. `hook-dispatch.mjs` passes `latch = false` for a plan-fence refusal carrying that mark, and for no other refusal, so every other refusal latches as before.

**What the check cannot see.** That the harness records a refused call in the agent's transcript as an error result. The read of `rulesWereRead` already relies on it for a refused Read, and `rulesRefusedBefore` relies on it again; if the harness did not record refusals as errors, every refusal would read as a first one and none would latch. The gate test fixes the transcript as the harness is believed to write it, and the first live send will show whether the second refusal latches.

**The general form.** A refusal that is only an instruction to the agent should not also close the route it instructs it to take. When a refusal is a way in, the text tells the agent the way, and the refusal sets the latch only once it has been ignored.
