## 403 · A plan's own script may run its steps with no turn of the manager between them, but only the script the owner read, byte for byte, and only behind a constant that stays off until a probe shows the fence holds an agent inside it

**Enforced by:** GATE hub:session-guards.test.mjs — the cases for the script gate (a Workflow refused while scripts are not accepted, whatever it carries; with them accepted, only the plan's `## Script` passed inline and byte for byte, with the hash the approval marker recorded, every agent told a literal plan path and a step of the plan's Steps that serves a goal, and no use of a word that reaches outside the script), for the marker (the script's hash recorded at approval by the tool and by the owner's exit in the app, moved by no amendment), and for the whole chain with the constant switched on in a copy, each with plants that take one check out and must fail it

**Recorded 2026-10-18.** Every step of a plan went through the manager: the manager sent it, an agent did it, the manager gave a status, sent a review, and sent the next. Each of those turns costs the owner's credit and the session's time, and a chain of steps that the plan already orders needs none of them between its members. The harness's Workflow tool runs agents in order from a script with no turn of the main thread between them. It had been refused outright, because a script carries instructions the owner has not read.

**What is accepted, and what it is held to.** A Workflow call whose inline `script` is, byte for byte, the plan's `## Script` section: the first fenced block there, or the section's own text, and only when it begins `export const meta` (`planScript`). The approval marker records the sha256 of that text when the plan is approved, by the tool and from the owner's exit in the app (`scriptHash`); an amendment of the Steps or the Order moves the marker's hash and never the script's, so a section edited after approval matches nothing and the call is refused. The call carries nothing else: no path to a script file, no resume of an earlier run, no arguments. The script is then read as a second lock (`scriptProblem`): every use of the word `agent` is a call whose first argument is a string literal, with no substitution in it, that is exactly the plan's path and the number of a step in its Steps that serves a goal; every `agentType` is a built-in one; the script uses none of `workflow`, `eval`, `Function`, `require`, `import`, `process`, `globalThis`, `constructor`, `__proto__`; it holds no regular expression literal, which the reader does not read and so refuses; and it starts at least one agent. The rules gate and the reads gate hold a Workflow as they hold a step.

**Why it is off.** Acceptance sits behind one named constant, `WORKFLOW_SCRIPTS_ACCEPTED`, and it is false. An agent a workflow starts must be held by the plan fence as an agent the manager sends is, and nothing yet shows that it is: the probe is to switch the constant on in a copy and run a one-agent script that attempts a command outside its step's Commands, and to read the hub's own logs for a refusal. Until that shows the fence holds, every Workflow is refused as it was.

**What the check cannot see.** A Workflow passes the dispatch gate without the pointer and the review gate, which judge the steps one at a time: the order inside a script is the order the owner read in the plan, and nothing re-derives it from the hand-backs. The lexer reads the forms a plan's script is likely to use, and refuses what it cannot read instead of guessing. And the constant being off means none of this has run against a real Workflow call.

**The general form.** A shortcut that removes the manager from a chain is acceptable when what it runs is exactly what the owner read and approved, when its hash was fixed at approval, and when everything that holds an agent in the ordinary path is shown to hold it in the new one; until the last is shown, the shortcut is built and switched off.
