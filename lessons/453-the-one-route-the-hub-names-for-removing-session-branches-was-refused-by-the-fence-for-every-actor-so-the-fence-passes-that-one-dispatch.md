## 453 · The one route the hub names for removing session branches was refused by the fence for every actor, so the fence passes that one dispatch

**Enforced by:** GATE hub:plan-fence.mjs — an agent's call of `mcp__github__actions_run_trigger` passes only when the method is `run_workflow`, the workflow is the file `branch-sweep.yml`, the repository is one the session holds (the origin of a repository the session names, read from its `.git/config`), and the text of the step the agent was sent for names `branch-sweep.yml`; every other run-trigger call, every other workflow and every other connector write is refused as before, and the main thread's manager fence and plan mode's reader list are not changed
**Enforced by:** GATE hub:session-guards.test.mjs — one case with five plants (the branch in the fence, the method, the workflow, the repository, the step text) seen red on each plant; the case holds a dispatch from a step naming the workflow passing, and a step that does not name it, no plan, an unreadable step, another workflow, a rerun, a failed-jobs rerun, a cancel, a log deletion, another repository, an empty call and six other connector writes refused, with the main thread's call and plan mode's classifier refusing the tool as before

**Recorded 2026-11-01.** Found in a review in an earlier plan and queued as Q-HUB-119. The hub's instructions name a dispatch of the branch-sweep workflow through the GitHub connector as the one route to removing a session's branches, because the git relay cannot delete a remote branch and the connector has no tool for it. The plan fence refused the connector's run-trigger tool for every agent, the manager fence refused it for the main thread and plan mode's reader list refused it for everyone, so the route the instructions named could not be taken by any actor and a session branch stayed on the remote. The earlier plan put the conflict to the owner once, and the answer was to pass that one dispatch and nothing wider.

**What is done now.** The fence reads four things on the call and the plan: the method, the workflow file, the repository against what the session holds, and the approved text of the step the agent was sent for. All four hold or the call is refused, with a refusal that names the first that fails. The step text is the plan the owner approved, so the dispatch is as much the owner's as any command the plan lists. A dispatch is a dry run unless the workflow's `delete` input is set, and the workflow looks only at `claude/` branches and removes one only when merging it into `main` changes nothing, so the pass reaches no branch the workflow would not itself judge.

**What the change leaves.** A sibling without a sweep caller cannot be swept, whatever the fence passes; `REPOS.md` lists which still owe one. The pass does not read the `ref` or the inputs of the call, since the workflow decides what to delete and not the dispatcher.

**The general form.** When an instruction names one route to an end and a gate refuses that route for every actor, the record holds a conflict and not a fix. Passing exactly the named route, from a step the owner approved that names it, closes the conflict; passing the tool, or any workflow, opens a second door nobody asked for.
