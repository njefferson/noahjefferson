## 405 · The harness judged an agent's commands itself and spoiled whole sessions, so each repository's settings allow the command shapes a plan lists, one rule each, and nothing broader

**Enforced by:** GATE hub:session-guards.test.mjs — the case that holds the hub's own `.claude/settings.json` to parsing, keeping its hooks, and allowing only `Artifact` and rules that each name one command shape, with a control that finds a bare `Bash`, a wildcard alone and a rule for a whole program in a planted list before the real file is judged

**Recorded 2026-10-18.** In the harness's automatic mode a call that no rule names is judged by the harness itself, and that judgement has spoiled whole sessions by refusing or holding an agent's ordinary command in the middle of a step. The harness's own page on session permissions gives the remedy: allow rules in `permissions.allow` of the repository's `.claude/settings.json` keep named commands out of that judgement.

**What was done.** The hub's and the app's settings each gain one rule for each command shape the plan's Commands section lists, written as a prefix rule (`Bash(git status:*)`), and nothing broader than a shape in that list. A shape that carries this session's id in a path under the scratch folder takes the shape of that folder (`/tmp/claude-0/`, with a wildcard where the session id was), so no rule carries a session id. A rule for a path under a tools folder is a prefix of that folder, which is wider than the plan fence's own check (the fence also refuses a path that climbs out of the folder, and still runs for every agent). The settings file was parsed after each write by a scratch script with its own control, and a file that failed to parse was put back, because the dispatcher skips a repository whose settings fail to parse and its hooks would go off with no sign.

**The claim, and the one thing not measured.** For a session launched inside the repository, the rules take the named commands out of the harness's own judgement. The same page says only a session with one repository reads the file. Whether the rules bind a session launched at the parent folder with several repositories under it, as the sessions of this family are, was not measured, and what would bind that session is the user-level settings file, which no plan has yet named in its Files. That is a choice for a later plan.

**What the check cannot see.** Whether the harness matches a prefix rule on the first word of a command line that begins with `git -C <folder>`, which is how agents write a git read; the rule is written for the shape the plan lists and the plan fence still decides what an agent may run.

**The general form.** A control the owner cannot read is replaced by a rule the owner can: the commands a plan names are allowed by name, in the file under version control, one rule each, and a check that the file still parses and still holds its hooks stands behind every edit of it.
