## 381 · Work running in the background is the work, and the session stays with it

**Enforced by:** GATE noahjefferson:stop-guard.mjs — refuses every stop while a task the session launched (a background command, a workflow) has no notification ending it and no TaskStop; a running agent is not counted among them; and refuses a turn that ends with steps of an approved plan unreturned, no agent of the session running, and neither a choice opening the reply nor a declared stop saying what is open · GATE noahjefferson:report.mjs — a status is due when an agent the session launched has ended since the last one, and each status prints how each agent ended, every hook refusal it received and its last tool result · JUDGEMENT

**Smell:** a turn ended under a declared stop while a workflow or background command the session started keeps running; a long gap between statuses with work in flight; the owner asking what the progress is; a turn ended with steps of an approved plan left and no agent running.

**Recorded 2026-10-02.** The five-minute status rule was enforced only by `report.mjs`, which refuses a tool call once five minutes pass without a status. A session that ends its turn makes no tool call, so nothing refused it. The session ended turns with "Stopping here" while two review workflows, a look re-fit and a long render ran, and gave no status for ninety minutes, then for another thirty, until the owner asked. The rule's intent covered that time, since the work was running; the session read its idle turns as outside the work. The stop hook now reads the transcript for every task the session launched and refuses the stop while one has not ended, declared stop or not. Measured on the session that prompted it: thirty launched, three still running, and those three named exactly.

**Amended 2026-10-04.** Two halves of that rule were wrong for agents, and one half was missing. An agent was counted among the tasks that hold a stop, so the main thread stayed in its turn between statuses and waited with a command of its own. A foreground wait ran past the Bash time limit at 07:05 on 2026-10-03 and was moved to the background, where it became one more task, and each wait cost a turn of the main thread's model. The harness's completion notification brings the session back when an agent ends, so a running agent no longer holds a stop: the main thread ends its turn after sending one. `report.mjs` no longer demands a status every five minutes either. A status is due when an agent has ended since the last one, and each status prints how each agent ended, every hook refusal it received and its last tool result, read from the agent's own transcript, and the approval state read from disk. The wait is not used any more; `report.mjs --wait` still exists and the manager fence still passes it. A background command or a workflow still holds the stop, as before.

The missing half was the opposite failure. A turn that ends with steps of an approved plan left and nothing running hands the owner back work the plan already gave, and on 2026-10-04 nothing refused it. `stop-guard.mjs` now reads the approved plan's steps and the agents the session sent, each prompt naming its step, and refuses the stop when a step has had no agent hand back for it, no agent of the session is running, and the reply neither opens with a choice for the owner nor declares the stop in its first line with what is open. An agent that ended at a refusal or an interruption returned nothing, so its step still counts as left and the main thread sends it again. A waiting owner message, a standing correction and a standing latch let the stop through, because each leaves the session no other move (Doctrine §0e rule 2).
