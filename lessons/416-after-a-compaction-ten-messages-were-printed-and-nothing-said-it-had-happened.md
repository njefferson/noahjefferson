The session still rebuilt the owner's settled instructions from the summary, because ten messages out of a long run is the summary's own mistake again at a smaller size, and nothing required the file to be opened. **What is done now.** `stretchSinceCompaction` in `compact-recall.mjs` reads every owner message since the previous compaction, or since the session's start where there was none, and numbers the compaction. `saveRecall` writes all of them, answered or not, whole and in order, to `recall/compaction-N.txt` under the session scratchpad; the print is still the newest ten with the count of the rest and the path. The file is a print of the session's own transcript for the session's own reading, and nothing copies it into a repository. `markRecallDue` records the file and the time at the start the compaction makes, and `recallGate` in `hook-dispatch.mjs` refuses every main-thread call but a read, the status and `TaskStop` until Read results covering every line of the file, returned after that time, are in the transcript (it uses `pageRead`, so a file too long for one Read is read in parts and still counts). It holds nothing while the file does not exist, it passes a subagent, and it does not latch. The same start records the compaction with its time (`markCompacted` in `report.mjs`). The first status after it prints "Compacted at HH:MM California time", once; the status page carries the same line under its updated line until a later compaction replaces it; and `stop-guard.mjs` refuses the first reply after it whose first line does not carry the word and the time, once, with the words to use. The line may share the first line with a stop declaration, and a follow-up that carries it discharges the refusal.

**What the check cannot see.** Whether the file was understood: a Read that returns every line counts, and the reading is the main thread's. A message longer than a line the Read tool returns may be cut in its result, which the line count cannot tell. A compaction with no scratchpad to file the messages in holds nothing, because the manager fence would not let the main thread read a file anywhere else.

**The general form.** A print bounds what is shown; a gate bounds what is acted on before the whole has been read. When a bound was chosen to save room, the part left out needs a gate of its own, or the bound is a way of not reading it.
