## 423 · A plan named five shipped roadmap items as work to build because it was written from the notes' roadmap and no gate read the app, so the plan gate now demands a read of the commit log and a statement, item by item, of what it showed

**Enforced by:** GATE hub:session-guards.test.mjs — the cases that take a plan through ExitPlanMode with a roadmap item marked in and the transcript holding or not holding a git log of the repository's two branches before or after the plan file's first write, with and without a Shipped check line; that pass and refuse the main thread's history reads through the manager fence, the hook and the check command; that refuse a review agent every write outside the scratchpad through the plan fence and the hook; and that feed the stop guard replies stating what a gate holds and replies instructing the owner, with plants in plan-guard.mjs, hook-dispatch.mjs, plan-fence.mjs and stop-guard.mjs for every part whose removal must fail a case · GATE hub:plan-guard.mjs — the refusal at ExitPlanMode, asked after the roadmap check · GATE hub:aim-review.md — the Sequence rule of the route check, which a reviewer applies and which a scratch script fired once on the first Order of the plan that added it

**Recorded 2026-10-24.** A plan approved on the morning of 24 October named five roadmap items as work to build: the button that takes a look off a photograph, the turn of an oval mask, the full view's Fit, the look file that opens on an iPad, and the Firefox start tiles. Each was already on the app's main, by a commit subject that names it and code that carries it. The plan had been written from the roadmap in the app's NOTES.md, a list kept by hand that had not been moved, and three reviews and every gate passed it. Every gate that read the plan read the notes. The roadmap check forced a line, in or out, for every open item. The What is check forced a quoted line from a file, and a quoted line from the notes' roadmap is exactly what the notes provide. The doctrine's rule 15 says a statement of state is read, never remembered, and the stop guard enforces it on replies; nothing enforced it on plans. Nothing read the app, whose state is its commit log and its code. A list in a file is a claim about them, and it was the claim the plan rested on.

**What is done now.** Four changes in the hub's guards and one in the review file, each with two cases in the guards' test and plants that take the part out.
- The plan gate, `shippedCheckProblem` in hook-dispatch.mjs, called by plan-guard.mjs at ExitPlanMode after the roadmap check. A plan with steps whose `## Roadmap` marks an open item of a repository's roadmap `in` is refused unless the session's transcript holds, after the plan file was first written, the result of a git log on that repository naming its production and its staging branch (`commitLogRead`, the branches read from the repository's `.branch-guard` by `repoBranches`, main and staging where it names none), and the plan's `## Shipped check` has a line for the item, `NNN: not shipped, read against main and staging on <date>`. A line saying `NNN: shipped on <branch> by "<subject>"` is refused as work already done. The refusal names each missing read and each missing or wrong line. A plan with no item marked in is not judged.
- The manager fence, `gitHistoryRead` in hook-dispatch.mjs, passes on the main thread a Bash line that is exactly `git -C <full path>` and log, ls-remote, branch in list mode or show-ref, on a repository of the session or the hub worktree in the session scratchpad, with arguments only from the subject format, the one-line flag, a count, the double dash, branch names and revision ranges. Every word of the line is of a set that expands and chains nothing, so a chained or redirected line, or a repository whose folder name carries a shell character, is still refused. Nothing else of git passes. The check command, `hook-dispatch.mjs --can`, calls the same fence and prints the same answer.
- The plan fence, `reviewWriteProblem` in plan-fence.mjs. An agent whose own transcript shows it was sent for a step the approval marker recorded as a review step is refused every write outside the session scratchpad, a Write, an Edit, a NotebookEdit, a Bash line that redirects output outside it and a git segment that is not a reader, with a refusal naming the review step, whatever the plan's Files and Commands allow.
- The stop guard, `goInstruction` in stop-guard.mjs. The refusal of a reply that asks for a go-word under a correction now fires only on a sentence that instructs the owner: the owner as the subject, or the imperative, with a verb of say, send, press, type, write or give and a go-word or approval as its object. A line opening Stopping here is not judged for it, and a clause stating that a gate holds something until a message carries a word is cut from its sentence first. It used to fire on the word go-word anywhere on the line, so a stop declaration saying what a gate holds was refused as though it asked for one.
- The review file, aim-review.md. Its route check gains a Sequence rule: a reviewer refuses a route whose Order puts in sequence two steps that share no repository and no dependency, naming them, unless the Order section says they run together. A scratch reading applied it to the first Order of this plan, four steps in the sequence hub, hub, app, app, and it fired on all four pairs of a hub step and an app step; the Order that replaced it fired on none.

**The excuse is the one the doctrine names.** The notes are the record a plan is told to rest on, and a list in the notes is a file with lines to quote, so the check was served to its letter and the premise was never tested. The reason is usually true as far as it goes. The test is whether the premise of the plan lies outside the plan, and the state of the app does.

**What the check cannot see.** It forces the read and the statement, and it cannot tell that a statement is true: a plan with the right words and a wrong line passes, and whether a commit subject names an item is a judgement that no parser makes, so the review and the audit make it. The read is of subjects and not of code; that the code carries an item is an agent's read. The history forms pass the fence on the main thread, but plan mode's own list of readers carries neither ls-remote nor show-ref, so in plan mode those two pass the fence and are refused by plan mode, and a standing correction holds every history read because it is not a read of the record. The narrowed go-word rule counts six verbs, so a reply, an answer or a response no longer counts as the owner's instruction. The Sequence rule is a reviewer's reading and no gate reads it.

**The general form.** A check that reads only the document a claim lives in cannot catch a claim that has gone stale. Where the premise of a plan is the state of something outside the plan, the gate has to demand a read of that thing, made by the session after the plan began, and a statement of what it showed, line by line; a quoted line proves that the line exists and never that it is current.
