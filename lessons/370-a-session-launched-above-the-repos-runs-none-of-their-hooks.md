## 370 · A session launched above the repos runs none of their hooks, and every rule then rests on memory

**Enforced by:** CHECKLIST — `HANDOFF.md` carries the approved gates (a user-level dispatcher, a five-minute report clock, talk-first and plan-names in `plan-guard.mjs`, a Drive guard, a third `stop-guard.mjs` shape, a post-compaction tool list). Each session's first plan clones the hub to `/root/.claude/hub` and installs the dispatcher from the clone; a write refused with "No approved plan is in force" is the proof that they are live. The rules themselves are Doctrine §0e.

**Smell:** the owner repeating a rule that a gate in this family already refuses. The gate is not failing; it is not running.

**Measured 2026-09-28.** A cloud session attached to two repos was launched in their parent directory, which has no `.claude/settings.json`. Claude Code loads project hooks only from the launch directory. The transcript held 543 Stop events and every one ran exactly one hook, the environment's own git check; `stop-guard` ran zero times, and so did `plan-guard`, `ident-guard`, `harness-guard`, the ledger and the session brief. The hub's CLAUDE.md had already recorded this for `branch-guard` alone.

**What ran in its place was memory, and memory failed on every rule it carried.** The same session proposed a plan with none of the five sections `plan-guard` requires. It worked for long stretches with no status. It asked questions the record already ranked. It searched the owner's whole Drive. It proposed an infrared white-balance test that moved only two of three gains. It told the owner a real field was invented, from a search of five files that left out the one holding it. And it told the owner a private folder could not be read, without trying the connector download it had, which worked first time.

**Two findings for whoever builds the gates.** A session's text between tool calls is in the transcript for only some messages (2,253 of 7,400 measured), so a gate cannot read chat to see whether the owner was told; it needs its own stamp. And a compaction summary can drop a capability in use, so the tool list must be re-printed after every compaction rather than trusted to the summary.

**And the same session handed the owner its own fix.** Having built the gates, it wrote the step that switches them on as the owner's — an edit to the environment's setup script, behind a menu the tablet app does not show — in a plan, a handoff and a report, without once trying the install itself; it tried only when challenged, and the harness refused it as self-modification. A route that asks nothing of the owner but the approve button already pressed had been listed an hour earlier and passed over. That is the Drive episode again from the other side: a limit asserted without a try, and the cost of it placed on the owner. `stop-guard.mjs` now refuses a reply that sends the owner to settings, a setup script, a menu, a permission rule or an install (shape 5, planted against three replies that session sent); whether a request is something only the owner can do stays a CHECKLIST line, rule 14 in `HANDOFF.md`.

**The approval half of the gates never approved anything.** `approved-plan-guard.mjs` was planted only on its refusal side: a write with no approved plan is refused, and it was. Nobody planted an approval. Its `--mark` looked for two phrases that exist only in the sentence the session is shown after approving, never in the result object a PostToolUse hook is handed, so two approvals wrote no marker and every write after both was refused. Read out of the installed Claude Code, the result is an object carrying the plan's `filePath`, and the marker is taken from that now (5c3b094, planted 21 ways). The first real approval afterwards wrote it. **A gate planted only in the direction it refuses has been half tested, and the untested half is the one the owner uses.**

**Installed mid-session, the gates went live at once.** The second session of the day cloned the hub, installed the dispatcher from the clone inside its first approved plan, and the next ordinary call was refused. No restart was needed, and the install was not refused as self-modification when a plan the owner approved named it. The same session then had three READS refused in plan mode by the gates it had just installed (a quoted pipe twice, `git -C` once), and found that a gate's own refusal of ExitPlanMode was being counted as the owner's answer. Both were fixed in the same session; neither could have been found while no hook ran.

**The harness said ultracode was off, twice, while it was on.** That notice is a harness bug, not a change of instruction. When it appears, the first line of the reply says so and the work continues with ultracode on (Doctrine §0e rule 9).
