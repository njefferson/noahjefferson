## 474 · The exits from plan mode of 5 November were recorded alike whether or not a button was shown, a plan ran on the top tier it had called unneeded, and a stop was held by the queue it was sent to answer

**Enforced by:** GATE hub:plan-guard.mjs — the plan gate refuses the approval call while the newest owner-typed message is recorded under auto mode
**Enforced by:** GATE hub:approved-plan-guard.mjs — the approval guard writes no marker from an end of plan mode recorded under auto
**Enforced by:** GATE hub:pending-guard.mjs — the pending guard lets the main thread's stop of a task through while a message waits
**Enforced by:** GATE hub:hook-dispatch.mjs — the dispatch gate sends no agent while the top tier serves
**Enforced by:** GATE hub:session-guards.test.mjs — each of the four has a case and a plant

**Recorded 2026-11-06.** Measured on 5 November, California time, in one session, from its transcript read whole.

**What happened.** A plan ran on an approval that the owner said no control had given. The transcript holds twenty-four exits from plan mode; fourteen were approved, and every approval is recorded the same way, as an allow-once from the approving device with the session as its scope. The two exits of that day are identical in every recorded field to one of 3 November that came thirty-seven seconds after the owner's own reject, and the harness version moved between them, from 2.1.317 on the press that showed a button to 2.1.318 on the two that did not. Every message the owner typed outside plan mode since 2 November, the ones after that 3 November press included, is recorded with the session's base mode, auto. Later the same day the approval guard wrote a marker from an end of plan mode that no exit call of the session had made: the owner-typed message before it was recorded under auto, and the owner said no plan-mode control was pressed. Two other failures sat in the same day. No send of an agent was held while the top tier served the main thread, after the session had said the work did not need it. And the owner's stop reached the session while a message of the owner's sat in the queue, which is the one state in which the pending guard holds every call, so the main thread's stop of a running agent was refused and the agent was ended by hand.

**What was wrong.** Three things were read as settled that were not. The record holds no mark that tells the owner's press from another answer, so a gate that waited for one waited for nothing, and an earlier claim that auto mode had answered the exits rested on nothing in the transcript either. The tier hold had been removed on the reasoning that a cost line answered it, and the line cannot stop a send. And the pending guard's hold had no pass for the one call whose purpose is to end work, so the owner's word stop and the guard that exists to deliver it met each other.

**The test.** An exit from plan mode is the owner's only when it is made with the session out of auto mode: the plan gate refuses the approval call while the owner's newest typed message reads auto, and the approval guard records no approval from an end of plan mode whose owner-typed message before it reads auto, saying so in its print. A send is refused while the serving model is a top-tier id, with the switch named and no latch. A stop of a running task passes the pending guard, whatever sits in the queue. Each refusal sets no latch, because the owner's switch or a later message answers it and a latch would only add a wait.

**The general form.** When the record cannot tell two acts apart, a gate must not be built on the difference; it must be built on a field the record does hold, here the mode on the owner's own message, and the cause of a surprising approval is read from the transcript before anyone is told what answered it. A guard that holds work for a message must pass the act that stops the work, or the stop and the hold wait on each other.

**What stays open.** The approval button that also enters auto mode leaves the session in auto, so the next plan's exit waits on a change of mode by the owner. Whether a button appears under the new harness version is the exit of the plan that built these gates, and its result is recorded at that plan's close.
