## 383 · After each compaction the doctrine was worked from a summary, and three sections were written into it on six lines read

**Enforced by:** GATE noahjefferson:doctrine-read-guard.mjs — every SessionStart, including the one fired after a compaction, writes a due marker, and while it stands the main thread may only read and give the status, until Read results on DOCTRINE.md returned after the marker cover every line

**Recorded 2026-10-02.** Doctrine §11e put its trigger at the start of a session and asked for the section list, one screen of headings, rather than the file. A compaction is not the start of a session as far as that wording goes, and nothing fired on one: the dispatcher's compaction branch re-printed the messages since the previous compaction (§376) and a census of the tools used earlier (§370), and nothing of the doctrine. Whatever the doctrine meant to the session afterwards was what the summary carried, which is a paraphrase written by the thing being governed.

**Measured on the session that prompted it**, by a harness over its own transcript that counts only the lines a Read result returned and skips errored results. It was made to fail first, on a synthetic transcript with known answers: counting a call's limit instead of its result, counting an errored read, and ignoring a compaction each gave the wrong answer.

The session ran three compactions in its first twenty-five hours and ten minutes. Before the first, four hours in, the main thread had read nothing of `DOCTRINE.md`, though the session's opening message asked for it first. Before the third, it had read two ranges: six lines, and fifty-five lines four minutes before that compaction summarised them away. A third Read in that stretch returned an error and nothing. The file was 2137 lines long when the six were read. In the same stretch three sections were committed into it, the California-time rule in §2 with §0f in one commit and §0g in the next, while the main thread had read six lines of it. After the third compaction the file was read in full, 2172 lines in five reads, in under four minutes.

So the one trigger the rule named did not fire in this session either, since nothing made it fire, and nothing at all fired at the three compactions. The failure §11e was written for, its own record of 2026-09-19, came back by the door the wording left open: a summary standing where the file used to be.

**The fix moves the trigger and the scope together.** §11e now fires at every session start and after every compaction, and asks for the whole file, because a section list says what exists and nothing about what it says. `doctrine-read-guard.mjs` prints one line at every session start saying the doctrine is due, and holds the main thread to reading and the status until the Read results returned after the marker cover every line, counted across as many reads as it takes, because the file is longer than one Read returns by default. Only the hub's own `DOCTRINE.md` counts, the one beside the gate in the clone every gate runs from, so a copy written elsewhere cannot clear it. Agents are not held to it: `plan-fence.mjs` holds them to the approved plan instead, and a full read per agent multiplies the spend §11b exists to restrain.
