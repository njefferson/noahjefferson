## 382 · Two failed routes were recorded as an impossible end, so a third was never tried and every branch removal fell to the owner by hand

**Enforced by:** GATE noahjefferson:.github/workflows/branch-sweep.yml — a workflow the session dispatches through the connector, whose own token removes a `claude/*` branch only when merging it into main changes nothing, and only while the branch still sits at the SHA that was judged · GATE noahjefferson:push-guard.mjs — only staging and main reach a remote, in every repo

**Recorded 2026-10-02.** On 2026-07-28 two routes to deleting a remote branch were tried and both failed. `git push --delete` through the session's git relay dies on a sideband disconnect and then prints `Everything up-to-date`, and the GitHub connector offers `create_branch` and `list_branches` and nothing that removes one (§8). The record drew its conclusion from those two and wrote it about the end rather than the routes: deleting a branch was a manual step for the owner, and the hub's CLAUDE.md told every session never to offer it. No session tried another route after that, because the record said there was none, and every branch removal in the family was the owner's, by hand, one bin icon at a time.

**A third route was never tried.** A workflow runs on GitHub's own runner, not through the relay, and its token's scope is set by the workflow's `permissions:` block, where absent scopes are none and `contents: write` is the one that writes refs (GitHub's GITHUB_TOKEN reference). The connector carries a workflow trigger. Neither recorded failure touched that path, and nothing in the record says it was ever tried.

**Meanwhile the branches kept arriving.** The harness names a `claude/*` branch in every repo, and only the hub's index said to ignore it; Jefferson-Photography-Studio's record said the session branch was where work belonged. The hub's remote held nineteen branches when it was first counted. Measured 2026-10-02 through the connector's branch list: the hub's remote holds five (one `claude/*`, three from Dependabot, and `main`), and Jefferson-Photography-Studio's holds twenty-five, twenty of them `claude/*`.

**The fix has two halves, because removal alone refills.** `push-guard.mjs` runs for the main thread and every agent. A `git push` must land on `staging` or `main`, and a push with no refspec or with `HEAD` is the current branch of the repo it runs in. Among what it refuses are `--all`, `--branches`, `--mirror`, `--tags`, `--follow-tags`, `--delete`, `-d`, `--prune`, a `:ref` deletion and a destination it cannot read without running the shell, and the connector's branch-creating tool, its file writes to any branch but `staging` or `main`, and its pull-request merge and branch-update tools. Doctrine §11 carries the full list.

`.github/workflows/branch-sweep.yml` removes what is already there. It looks only at branches under `claude/*` and prints every other branch as out of scope, untouched. A branch is removable only when `git merge-tree --write-tree` against main exits 0 and its whole output is exactly main's tree id, so merging it into main changes nothing. A conflict exits 1 and still prints a tree, and an unrelated history exits 128, so the exit code alone is not the test; both keep the branch, printed with the count of commits main lacks. Main is the only base, because staging's history is disposable. A dispatch is a dry run unless its `delete` input is set. Then a separate step deletes each removable branch whose name matches `^[A-Za-z0-9._/-]+$`, by a push of `:refs/heads/NAME` with a lease at the SHA that was judged and the token in an auth header scoped to that one command, so a branch that moved since it was judged is refused rather than deleted; any other name is kept and counted as a failure. That step is not the only one given the token. The checkout step receives it too, because checkout fetches with the job's token by default and here that token carries `contents: write`; `persist-credentials: false` removes it from `.git/config` when the checkout ends, so the judge step holds none, and after the checkout the deletion step alone is given it. The token's scope is GitHub's documented behaviour and not yet a measurement here: the first deletion is read off the remote before any other runs.

**The general form.** A record that a route failed names the route. Written as "a session cannot", it closes every route to that end, including ones nobody tried, and the closed end lands on the owner as manual work. Doctrine §0e rule 7 already says a limit is reported only after every available route was tried; this is what the same error looks like once it is written into the record and inherited.
