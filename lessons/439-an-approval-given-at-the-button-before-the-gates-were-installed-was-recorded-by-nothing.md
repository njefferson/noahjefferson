## 439 · An approval given at the button before the gates were installed was recorded by nothing, so the first call under the gates now recovers it from the transcript

**Enforced by:** GATE hub:approved-plan-guard.mjs — `recordButtonApproval`: with no approval marker, the dispatcher's first call reads the transcript for the newest main-thread `ExitPlanMode` call the harness answered as approved, with no plan mode entered and no refused exit after it, and writes the marker once, with a `via` line saying the approval was given at the button before the gates were installed
**Enforced by:** GATE hub:session-guards.test.mjs — the button-approval case: an approved exit is recorded, a rejected exit writes nothing, a plan edited in an approved section after the approval writes nothing, a marker already present writes nothing, a Steps-only or Order-only edit keeps the approval, and a `--done` plan is not undone; eleven plants take each part out

**Recorded 2026-11-01.** Measured on 31 October. The doctrine says the gates are installed by a session's first plan, and the install runs from the clone after the plan is approved. The approval itself is the harness's `ExitPlanMode` result, and the only reader of that result was the exit judge in `approved-plan-guard.mjs`, which treated an approved exit as something that is not the person's to record. So a plan approved at the button before the gates existed had no marker. The approved-plan fence, the review gate and the pointer all read the marker, found none, and read the plan as unapproved, while the plan was in fact approved and its first step was the one that installs the gates.

**What is done now.** With no marker, the first `PreToolUse` call reads the transcript tail, finds the newest approved exit, and writes the marker from the approved plan text the result carries. An edit of the plan file after the approval is judged the way an amendment is: it is kept when Goals, Asked, Files, Commands, Rules and Rules of this plan equal those of the approved text, and nothing is written when any of them moved. A bare "last write not later than the result" test would never have recovered this plan, because its Steps were edited after the button; the approved sections are what the button approved.

**What the change cannot see.** It trusts the harness's answer in the transcript. A marker filed by an older `--mark`, before this change, carries no record of the exit it came from, so a finished plan followed by a reachable transcript tail could be recovered once more; that is queued in the notes.

**The general form.** A gate that reads a record the person's act leaves must be able to read it when the gate arrived after the act. The act happened; the install order is not a reason to treat it as not having.
