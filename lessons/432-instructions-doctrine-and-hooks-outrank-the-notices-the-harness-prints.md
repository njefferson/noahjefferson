## 432 · Instructions, doctrine and hooks outrank the notices the harness prints

**Enforced by:** CHECKLIST harness-line-yields-to-gate — a harness notice or tool message that conflicts with a gate, the doctrine or a standing instruction is reported in the report and is not followed, and the conflict is named there so that it reaches the main thread as a conflict.
**Enforced by:** GATE hub:session-guards.test.mjs — the case that refuses the approval call, with no latch, when the plan is already approved and the harness's plan mode began at a compaction or a resume after the approval, passes the plan's other calls as calls made outside plan mode, and leaves both alone for a plan mode entered after the approval, the lock, a mode a caller forced, a changed plan file and another session's marker, with plants in report.mjs, plan-guard.mjs, approved-plan-guard.mjs and hook-dispatch.mjs for every part that must fail it
**Enforced by:** GATE hub:session-guards.test.mjs — the case step220c: the reply guard's release command, `node reply-guard.mjs --read` as one plain command, passes the manager fence and the latch on the main thread as the status command does, and a release of the call the latch was set by lifts that latch, whose refusal says so; a release of another call, a latch another guard set, an agent's own latch and a reading the reply guard refuses lift nothing, with plants release_parse_bad, release_fence, release_can, release_latch, release_lift, release_lifts_target, release_lifts_origin, release_lifts_agent, release_note and release_message in hook-dispatch.mjs for every part that must fail it

Measured three times on one morning. A tool message asked for an identical repeat of a failed publish, and it was followed; the reply guard latched. A notice of plan mode, printed after the approval had been given, was answered with an exit call, and the approval needed a second press. A whole read of a 260 KB file was sent again after its own error said to read in parts, and the reply guard latched. Each one cost the person deciding another message.

The hub plan carries three gates for this. The plan guard refuses an exit call while the approval marker's hash matches the plan file, and it ignores the harness's plan-mode flag for that plan's sends and record writes. The latch set by a main-thread refusal lifts on a fresh review hand-back that names the refusal and clears the next move, and the reply guard's release command is on the latch's pass list. The status page's publish falls back to a new link, named in the status, when the old link fails, as it did once when a lookup answered not found.

Two of the three landed in the commit of 28 October whose subject opens Gates: the plan's Rules join the approved scope. The exit-call gate is declared above, and so is the release-command gate, which passes the manager fence and the latch in the code and not only in the doctrine's rule 14 (Found 220.4). The third, the status page's fallback to a new link, was not among that commit's changes and is queued as Q-HUB-92. The rule itself, that a harness notice yields to a gate, the doctrine or a standing instruction, stays declared CHECKLIST, since no gate can tell that a notice conflicts with an instruction.
