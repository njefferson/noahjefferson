# The hub rebuilt on the harness's own parts

This is the design and the order of work for rebuilding the hub on the harness's own parts, and hub work starts from it.

## A. How a piece of work goes

The owner says what is wanted. The session scopes it and writes back one page: the result as something that can be seen, how it will be checked, the steps in a few lines, the cost, and the way back if it goes wrong. The owner approves once. The work runs to its end without the owner: workers on the cheapest tier do the steps, the top tier is consulted only at hard decisions, and no message, go-word or switch of model is needed. Before anything reaches the owner, a checker that did none of the work opens the real output and judges it against the stated result, and a push is refused until it has. The owner gets the result and what the check showed, and during the run only a choice that is the owner's comes back.

## B. What the harness gives

Read from its documentation on 11 November. Its own summary of its design is three things: tell the session what it cannot see, give it a check to run, and enforce the rules that can have no exceptions. The instruction file is loaded by the main thread and by every agent, each line of it takes attention on every task, and a line that keeps being ignored is either lost in a file grown too long or is a rule for a hook. A plan can run as a script that the harness executes in the background, the steps in order with an agent for each and agents that check other agents' results, with no turn of the main thread spent per step and no input once it starts. A session can be held to a stated condition that a fresh model checks after every turn. A cheaper model can consult a stronger one at hard points by itself. The main thread can run as a defined agent whose tool list names the only agents it may send, and an agent definition carries its own model, tools, memory and limit of turns. A procedure belongs in a skill, whose body loads only when used. A cloud session takes its agents and its configuration from the repository.

## C. What each repository holds

One short page: what the owner wants, how a session works for the owner, and the few never-rules. Three roles as the harness's own definitions: a manager that plans and judges and cannot edit, a worker, and a checker that can read and run and cannot edit. Hooks only for the rules with no exceptions: where a push may go, nothing personal in a repository, and the check before a push. Procedures, a release, a cold read and an accessibility walk among them, as skills.

## D. What is retired and what stays

Retired once the trial has shown the new way to work: the holds at each message, the go-words, the latches, the gate on tiers, the review before each move, the plan check's sections, the seed, the findings queue as a queue of work, and about five thousand lines of pages. Staying: the push guard, the branch guard, the checks of privacy, quotation and the third person, the check of a commit's message, the checks that run in the repositories' own workflows, the program as the ranked list of the apps' work, and the lessons as an archive that no session loads.

## E. The order

First, this plan: the stand-down. Second, under the stand-down, the parts of Part C are built in the hub repository as one piece of work scoped on one page and approved once. Third, one real piece of work is taken through them from approval to a checked result, the first being the rule of the seed's standing text that gave the device the first look at what a session built. Fourth, what that cost in the owner's acts, in stops and in tokens is set beside the hub's own record and reported. Fifth, the other nine repositories. Sixth, the retirement of Part D.

## F. Not verified, and settled by the trial

That a cloud session honours each part of Part B as documented, that the stronger model is available as an adviser on the owner's plan, and how the shared parts reach all ten repositories.

## G. Where the work stands

The first act, the stand-down, landed on 11 November 2026 and is in force through 18 November. It took eleven agent sends and about four hours, and it met two refusals.

The second act is built. The two roles, the worker and the checker, are installed under the configuration folder's agents folder and loaded within the session that installed them, about ten minutes after they were written. The two procedures, piece-of-work and landing, are installed under its skills folder and were picked up within the same session. The short page stands at plans/native/page.md, and the roles name it by that path.

The check before a push is in the push guard and acts only under a stand-down. While one is in force, a push of main is refused until an agent that changed nothing has given CHECK PASS and the full id of the exact commit being pushed, as the first line of its hand-back or of its final message, read from the session's agent transcripts and never from a file. With no stand-down the push guard decides as it did.

The install was made in accept-edits mode, where the harness asked the owner before each of the five writes to its configuration folder. The fifth was a list of the hub's own test and check commands, so the build ran without asking.

The trial has shown two things so far. In auto mode the harness's own check refuses an agent's write under the configuration folder, and it refuses to start an agent whose task is to change the session's own roles or gates, so those changes are placed by a person's approval and agents only draft them. A new agent type in a folder that did not exist at a session's start loaded within the same session, though the harness's documentation says it waits for the next start.

What remains for a person to switch on is running the main thread as a manager role, and naming a stronger tier as its adviser.

The third act was made on 11 November 2026 and was the first piece of work taken through the two roles. The rule that gave the device the first look at built work is rewritten in the seed's standing text, in two paragraphs of the plans page, in the apps page and in one line of the instruction file's index: a checker that did none of the work opens the built thing in the container before a build is handed over, what only the device can show is measured on the app's test page, and the walks still run once at the promotion to main. Q-HUB-533 is put right by it. What the piece cost is reported for the fourth act.

The harness's own check refused twice in these two acts: in the third it refused the worker's pull that brings a container's copy of the gates forward, after the push had gone through and with no gate code changed; in the fourth it refused to start an agent whose task was to add two lines to the hub's list of allowed commands, so the list was left as it was.

The fifth act. On 11 November 2026 a page was put up under this act's name that would have spread the stand-down to the other repositories. That was not this record's fifth act. The harness's own check refused to start the agent for it, and nothing of it was built. What that night's commit did build stands: under a stand-down the check before a push holds a push of staging as it holds a push of main and refuses the connector's file writes to either, and the roles and the procedures stand in a form that holds in any repository, as plain files under plans/native/roles and plans/native/skills.

How the nine repositories get the parts. The harness's documentation, read on 12 November 2026, says a session with several repositories starts above the clones and reads no hooks, permissions or roles from a repository's own configuration folder, and the other repositories' sessions are started that way, with the hub beside the app. So the parts reach them through the hub's copy in each session's container: the short page, the two procedures and the two roles as files there, and the push guard and the check before a push through the hub's hooks. A role loads as the harness's own definition only in a session started in the repository that holds it, and a session started above several repositories gives its agents the role files by their paths. The stand-down freed the hub's own session for the trial and no other, as it was designed to.

The sixth act began on 12 November 2026 with the switch. For every session, in every repository, the hub's hooks now do what they did under the stand-down, the check before a push always acts on staging and main, the hub's copy is brought forward at a start or resume, each repository's own hooks still run, and each prompt prints one line that names the short page. The code, the cases and the pages of the retired gates are removed in the step after the switch has been seen working in a session outside the hub.

Notes from the Quietkeep session of 11 November 2026 are filed in the hub's record: its finished work as P-585, and three findings as Q-HUB-532 to Q-HUB-534 with P-586 to P-588. The finding on the seed's rule about renders (Q-HUB-533) joins the third act, and the session's cost figures stand in the close entry under the measure item P-10 for the fourth act. The photography session's eight matters of 11 November, with one more passed in after them, are filed as Q-HUB-535 to Q-HUB-543 with P-589 to P-597, matter 1 (Q-HUB-535) bearing on the check before a push and joining the third act. The program entry and close for that session's two plans of 11 November wait on that session passing in their text.

The removal followed on 12 November 2026. The hub's hooks are now one small dispatcher that refuses the choice popup, runs the push guard with the check before a push always on, brings the hub's copy forward at a start, runs each repository's own hooks and prints one line naming the short page. The plan guard, the stop guard, the start brief and the plan-scope check remain as shells, because other repositories call them by their paths. Every other hook and gate is deleted with its cases and plants, and the stand-down question with them. The hub's instruction file is the short page and a list of where things are. Its sections on things that stay are in HUB-REFERENCE.md, and the old instruction file, the plans page and the pages of the retired gates are in the archive folder as they were written.

The proof. On 12 November 2026 a fresh session of the photography app's repository cloned the hub at 3240ced and installed its hooks. A plain command passed with nothing printed. A push of staging with no checker's pass and a push to another branch were both refused before git ran. The app's own commit check called the hub's plan-scope shell and passed. The app's plan guard passed a write in plan mode and refused the choice popup. The start brief printed the branch lines and the line naming the short page. An agent given the worker role by its path did its step for about 83,000 tokens. The gates run for 3240ced was green in under two minutes, where the old suite took about forty-five.

The project is closed. A session in any of the ten repositories now runs the hub's one dispatcher, the push guard with the check before a push, the four shells and that repository's own hooks, and works as the short page says. The stand-down file has nothing left to free and is to be deleted.

Left for the next project, which starts with its own record: a brand-new container gets the hub's hooks only when something installs them, since the old first-plan step that did so is retired; each app's session is to be started with that app alone, so its own roles and settings load; an environment's setup script is the place that installs the hub; and each app's own instruction file still describes the old way and is to be shortened by that app's session. The hub's own instruction file lists a page that still describes the old gates in part, doctrine/never.md, and the two written rules of 12 November are not yet in the hub's installed copy of the managing procedure under its configuration folder.
