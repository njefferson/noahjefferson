# The plan seed's standing text

The owner edits these words and `plan-seed.mjs` reads them: each block opens with a line of two at-signs and its name, and runs to the next such line. A word in curly braces is filled by the seed at the time of the print: HUB (the full path of the repository the print is for, the working copy and never the live clone), ITEM (the program key), TAKEUP, CLOSE and REVIEW (the step numbers), NEXTP (the next free program key), NEXTQ (the next free found key), NEXTL (the next free lesson number), TRANSCRIPT (the session's transcript path), REVIEWFILE (the review's full path) and PUTRIGHT (empty, or in a batch print the paragraph that sets the items of findings whose own text says they were put right to done at the take-up, each with that sentence as what changed) and LANDING (the landing block below, whole, which ends in the pull of the live clone) and TAKEUPLANDING (the take-up's landing block below, whole, which pulls nothing), and in a batch print FINDKEYS (the finding keys of the items the take-up sets to planned), LANDSTEP (the landing step's number, which is also CLOSE), FIRSTGROUP and LASTGROUP (the first and last file step), GUARDFILES (the files whose plants the landing step runs), LANDEST (the landing step's estimate in minutes) and CHECKS (the seven hub checks as their usage spells them). Nothing above the first block is printed.

@@ rules-of-this-plan
- Every step runs on the sonnet tier; the main thread manages and does no step.
- The agent's first call is the Read tool on `/root/.claude/hub/agent-rules.md`, made alone, with no other call in the same turn; a first call sent beside another was refused and latched an agent on 3 November.
- Each step has four parts the agent reads before acting: Facts, what the step depends on, restated; Do, the exact actions; Observe, what must be seen for the step to be DONE; Kill, what ends the step with nothing further written. On a red check or an observation that is not the one named, the agent writes what it saw into its report, hands back FAILED naming it, and writes nothing after. An observation the step did not foresee, or a judgement the step does not settle, hands back EJECT with what was seen and the files named, and writes nothing after.
- Every report's first line after its verdict word is the wall line: one sentence answering whether the step still serves this plan's goal 1, whether that goal still serves the program's thesis, and whether what was seen moved either.
- Every file is read with Read or Grep and written with Edit or Write; each shell line is one command from Commands, with no `cd`, no variable assignment in front of it, no semicolon, no `&&`, no pipe and no redirect; git is written bare, and the shell already starts in the repository the plan names, so git and the checks run as the Commands list them with no change of directory first; that holds for a session launched inside the repository, and a session launched at the parent folder of several repositories starts its shell at the parent, where a bare git line fails with nothing changed, so each git line on the repository there carries git's directory flag and the repository's full path while the Commands entry stays bare, which the plan fence reads away before matching; the live clone's lines carry the flag and its full path in every launch. Every git read is bare, with commit ids and plain flags, and carries no format string and no percent code.
- No run of this plan goes in the background. Every run of the suite and of a check is made in the foreground with the Bash tool's timeout set to ten minutes, and a run that ends on that timeout ends the step EJECT naming it.
- No file quotes the owner. An event is named by its California date and time, never by an agent's or a task's id, and no run of seven or more hex-set characters is written that a command in that agent's run did not print.
- A string a case writes holds no word the third-person check reads as a pronoun, whole or as the first part of a word split across a template.
- Each commit is made under the container's default git identity with a plain, reader-facing message carrying no chat link, no model's name and no trailer of any kind, whatever the harness's attribution reminder asks. A commit with a wrong message is never amended, because the harness's classifier refuses an amend as destructive and a send is spent on the refusal: it is replaced by new commits made from its diff, in the live clone, and pushed from there. Nothing is pushed except by the take-up step and by the landing step, which is the close step in a plan for one item; each fetches the remote's main, puts its commits on top of it with a rebase, and pushes main as a fast-forward, never forced. Where the last rebase of the landing step stops on a conflict in `PROGRAM.md` alone, the step resolves it with the Edit tool so both sessions' items stand, the other session's entries as the remote's head holds them and this plan's after them, each count line raised by this plan's number over the remote's figure, and every program or found key of this plan the remote's head already holds moved to the next free key past the remote's, in `PROGRAM.md` and in each file of this plan that names it, the report naming each move; then `git add` naming each file changed, `git commit -m` with the commit's own message and no path after it, and `git rebase --continue`; a conflict in any other file, or in any other rebase of this plan, ends the rebase with `git rebase --abort` and the step ejects with nothing pushed.
- A send after the first of any step reads that step's report and `git status` first, does again nothing the report says landed, and starts from the list of what remains that the report gives. A send after the first writes its own report file, named for the step number, a hyphen, the send's number and then -report.txt, so no send overwrites an earlier one's Found lines, and its report carries every Found line of the sends before it.
- Each hub check is spelled as its own usage text gives: the docs check takes the repository's full path bare, and the quote, privacy, third-person, example and pin checks take the repository's full path after their repo flag; where an agent is unsure of a check's form it runs the check with its help flag once and reads the usage before the first run.
- A step that edits a guard file the suite covers runs every case of the suite, with no case filter, once after its last edit and before its commit, because a step that ran only its own new cases left an existing case stale and the runner was the first to see it red.
- A step that adds a refusal to the plan fence lists `hook-dispatch.mjs` among its files, because the dispatcher decides separately which refusals set a latch, by the fixed words of each refusal, and the plans page names that list beside the fence's refusal rule.
- A line a fix needs in a file another step owns is named in the report with the file, the place and the exact words, for the landing step, and is not written by the step; the step ejects only where its own part cannot be made or proved without that line.
- In the landing step every edit of a gate file is made before the run of the whole suite, and a run of the whole suite, of a file's plants or of a check that comes back red, names a missed plant or exits other than 0 ends the send FAILED with nothing written after but its report, which names each case, plant or check line to put right and the file each sits in, so the next send puts them right first; the fence refuses an agent's write after its own red run of the suite and its commit of a gate file it edited with no run of the whole suite after the edit. The plants of every edited file run there narrowed to that file, but for the long files, which are `hook-dispatch.mjs`, `session-guards.test.mjs`, `report.mjs` and any file whose dry listing counts more than two hundred and fifty plants: of a long file only the new plants run, by key, and its other plants are proved by the runner's doctrine gates run after the push.
- A step that needs a number from the device names the app's test page as its instrument and never a container render, and no accessibility walk, cold read, browser walk or screenshot tour runs against a staging build or a test page as a step of a plan: the gate runs once, over the integrated release, at the promotion to main.

@@ parallel-rules
- The file steps, {FIRSTGROUP} to {LASTGROUP}, run at the same time in the one working copy. Each writes only the files its own text names, commits nothing and stages nothing, and reads `git status` as showing changes to its own files and to files the other file steps own, which it does not touch; a change it did not make to a file no step of this plan owns ends it EJECT naming the file. Each edit it makes leaves its file whole, so a run another step starts in that moment reads a file that loads. It works in this order and no other. First, every edit its findings ask for, its cases and its plants written. Second, for each assertion of a case it wrote or changed, the helper or guard function the assertion calls read with Read and Grep and the assertion checked against that code, any it does not bear out put right before anything runs. Third, the third-person, privacy and quote checks once each, any find in a line the step wrote reworded with no string the code matches changed, and a find in another step's file named in the report and not acted on. Fourth, its own cases, each in a run of its own with one case switch to a run. Fifth, its own new plants, by the plants switch and the switch that names plant keys, followed by those plants' keys joined by commas, each key copied from the file that holds the plant: that run exits 0 whatever it finds, so the step reads each plant's line, and where a line says MISSED the case asserts too little, the step strengthens the case in its own file and makes that run again until every new plant reads CAUGHT and the run's last line counts none bad and no leak. Sixth, the suite's dry listing, the plants switch with its dry switch and the files switch naming the files it edited, made once: a plant the listing names as stale is re-pointed with the Edit tool where it sits in a file the step owns and then run by its key and read as CAUGHT, and is named in the report with its file and the edit to make where it sits in another step's; the listing is not made a second time by the step. A red run of a case of its own ends the send FAILED with the report naming the fix, because the fence refuses every write after it.
- A review for a resend of a file step is sent only when no agent is editing the working copy, which is after every file step of the batch has handed back, because a review sent while a sibling step still edited judged a state that moved under it and bought nothing.
- Where a step of the batch changed code so that an existing case no longer holds, the landing step puts the code right in the owning step's file and keeps the finding's fix, and where the finding asks for the changed behaviour the landing step brings the case to it, with no assertion that a gate refuses something removed or loosened.
- A landing step with several commits stages nothing beforehand and names each commit's own files after the message, because the Commands hold no unstage; a new file is staged with `git add` naming it just before the commit that holds it.
- A suite case never writes into the working copy: a case that needs a program, a found folder, a lessons folder, a plan file, a marker, a repository or a transcript writes it under a temporary folder and removes only that folder.
