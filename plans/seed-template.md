# The plan seed's standing text

The owner edits these words and `plan-seed.mjs` reads them: each block opens with a line of two at-signs and its name, and runs to the next such line. A word in curly braces is filled by the seed at the time of the print: HUB (the full path of the repository the print is for, the working copy and never the live clone), ITEM (the program key), TAKEUP, CLOSE and REVIEW (the step numbers), NEXTP (the next free program key), NEXTQ (the next free found key), NEXTL (the next free lesson number), TRANSCRIPT (the session's transcript path), REVIEWFILE (the review's full path) and PUTRIGHT (empty, or in a batch print the paragraph that sets the items of findings whose own text says they were put right to done at the take-up, each with that sentence as what changed) and LANDING (the landing block below, whole), and in a batch print COMMIT (the commit step's number), FIRSTGROUP and LASTGROUP (the first and last file step), GUARDFILES (the guard files the file steps edit), COMMITEST (the commit step's estimate in minutes) and CHECKS (the seven hub checks as their usage spells them). Nothing above the first block is printed.

@@ rules-of-this-plan
- Every step runs on the sonnet tier; the main thread manages and does no step.
- The agent's first call is the Read tool on `/root/.claude/hub/agent-rules.md`, made alone, with no other call in the same turn; a first call sent beside another was refused and latched an agent on 3 November.
- Each step has four parts the agent reads before acting: Facts, what the step depends on, restated; Do, the exact actions; Observe, what must be seen for the step to be DONE; Kill, what ends the step with nothing further written. On a red check or an observation that is not the one named, the agent writes what it saw into its report, hands back FAILED naming it, and writes nothing after. An observation the step did not foresee, or a judgement the step does not settle, hands back EJECT with what was seen and the files named, and writes nothing after.
- Every report's first line after its verdict word is the wall line: one sentence answering whether the step still serves this plan's goal 1, whether that goal still serves the program's thesis, and whether what was seen moved either.
- Every file is read with Read or Grep and written with Edit or Write; each shell line is one command from Commands, with no `cd`, no variable assignment in front of it, no semicolon, no `&&`, no pipe and no redirect; git is written bare, and the shell already starts in the repository the plan names, so git and the checks run as the Commands list them with no change of directory first; that holds for a session launched inside the repository, and a session launched at the parent folder of several repositories starts its shell at the parent, where a bare git line fails with nothing changed, so each git line on the repository there carries git's directory flag and the repository's full path while the Commands entry stays bare, which the plan fence reads away before matching; the live clone's lines carry the flag and its full path in every launch. Every git read is bare, with commit ids and plain flags, and carries no format string and no percent code. A run that may pass ten minutes goes in the background, and three calls around it each stand alone in a turn of their own: first the progress note, written in the scratchpad's progress folder with a line opening with the word label and a colon naming the run and, where the command line names its own output file, that file's full path, and no time; then the launch, as the one call of the next turn; then the note written again with the full path the launch printed, as the very next call after the launch and before any other call, because a read of the output sent before that second write is refused and a second refusal latches the agent; then the agent ends its turn on the run with no loop and no wait of its own, its completion resumes it, and it reads the run's output file whole with Read and Grep.
- No file quotes the owner. An event is named by its California date and time, never by an agent's or a task's id, and no run of seven or more hex-set characters is written that a command in that agent's run did not print.
- Each commit is made under the container's default git identity with a plain, reader-facing message carrying no chat link, no model's name and no trailer of any kind, whatever the harness's attribution reminder asks. A commit with a wrong message is never amended, because the harness's classifier refuses an amend as destructive and a send is spent on the refusal: it is replaced by new commits made from its diff, in the live clone, and pushed from there. Nothing is pushed except by the plan's landing steps, which are the take-up step, a commit step where the plan has one, and the close step; each fetches the remote's main, puts the commits on top of it with a rebase, and pushes main as a fast-forward, never forced; a conflict ends the rebase and the step ejects with nothing pushed.
- A send after the first of any step reads that step's report and `git status` first, does again nothing the report says landed, and starts from the list of what remains that the report gives. A send after the first writes its own report file, named for the step number, a hyphen, the send's number and then -report.txt, so no send overwrites an earlier one's Found lines, and its report carries every Found line of the sends before it.
- Each hub check is spelled as its own usage text gives: the docs check takes the repository's full path bare, and the quote, privacy, third-person, example and pin checks take the repository's full path after their repo flag; where an agent is unsure of a check's form it runs the check with its help flag once and reads the usage before the first run.
- A step that edits a guard file the suite covers runs every case of the suite, with no case filter, once after its last edit and before its commit, because a step that ran only its own new cases left an existing case stale and the runner was the first to see it red.
- A step that adds a refusal to the plan fence lists `hook-dispatch.mjs` among its files, because the dispatcher decides separately which refusals set a latch, by the fixed words of each refusal, and the plans page names that list beside the fence's refusal rule.
- A step that needs a number from the device names the app's test page as its instrument and never a container render, and no accessibility walk, cold read, browser walk or screenshot tour runs against a staging build or a test page as a step of a plan: the gate runs once, over the integrated release, at the promotion to main.

@@ review-step
{REVIEW}. **Review.** Hub, one agent per send, Standing. Follow {REVIEWFILE} by that full path for the move the manager notes' unnumbered `Next:` line names, and hand back its verdict line first. This step is never a resend: a send of it reads no step's report as its own and does none of any step's Do, and it follows the review file from its first line whatever the manager notes say was sent before. The review judges that move and does none of it: it does not carry out the Do of the step it judges, runs none of that step's commands, starts no background run, and writes nothing but its own record in the scratchpad's `progress/` folder. Every file, the repository's own files and its git configuration among them, is read with the Read or Grep tool. The only shell lines are the one `node` command on the review's script under the scratchpad and a single git read the agent rules list; its git reads are bare, `git status`, `git log`, `git show` or `git rev-parse` with commit ids and plain flags, and carry no `--format` or `--pretty` string and no percent code; each shell line is one command, with no `cd`, no variable assignment in front of it, no semicolon, no `&&` and no pipe.

@@ parallel-rules
- The file steps, {FIRSTGROUP} to {LASTGROUP}, run at the same time in the one working copy. Each writes only the files its own text names and, where it names one, its own case file under the guard cases folder, commits nothing, stages nothing, runs no plants and no check, and reads `git status` as showing changes to its own files and to files other steps of this plan own, which it does not touch; a change it did not make to a file no step of this plan owns ends it EJECT naming the file. Its one run of the suite is its own cases by name, once, after its last edit; this replaces the every-case rule above for these steps, the commit step running every case. A red case whose error names a file the step did not edit is written into the report with the file's name and the step that owns it, and the resend runs the cases again before it edits anything.
- A review for a resend of a file step is sent only when no agent is editing the working copy, which is after every file step of the batch has handed back, because a review sent while a sibling step still edited judged a state that moved under it and bought nothing.
- Where a step of the batch changed code so that an existing case no longer holds, the commit step puts the code right in the owning step's file and keeps the finding's fix, and where the finding asks for the changed behaviour the commit step brings the case to it, with no assertion that a gate refuses something removed or loosened.
- A landing step with several commits stages nothing beforehand and names each commit's own files after the message, because the Commands hold no unstage; a new file is staged with `git add` naming it just before the commit that holds it.
- Plants run only in the commit step, one guard file per background run and never several files in one process, because the suite's heap grows across plants; before a plants run the commit step reads every plant of the files the batch edited whose target line an edit changed and moves that plant's find to the new line.
- A suite case never writes into the working copy: a case that needs a program, a found folder, a lessons folder, a plan file, a marker, a repository or a transcript writes it under a temporary folder and removes only that folder. After each run of the cases and each run of the plants the agent reads `git status`, and a tracked file deleted or changed that no step of this plan owns ends the step EJECT naming the files.

@@ commit-step

Facts: steps {FIRSTGROUP} to {LASTGROUP} left their edits uncommitted in the working copy, each report listing its files, cases and plants; every case runs once here over all their edits, as every landing runs every case before its push; the plants of each edited guard file run here for the first time, one guard file per background run, the files being {GUARDFILES}; an existing case red under the edits is put right here, in the owning step's file where that step changed code so that the case no longer holds and the finding did not ask for the change, and in the case itself where the finding asks for the very behaviour the case asserts against, with no assertion that a gate refuses something removed or loosened, each such edit named in the report beside its case and going into the commit of the step whose file or finding it meets; a plant missed means a case asserts too little, and this step strengthens that case in its case file and runs that file's plants once more; the remote's main moves under this session. Do: read the reports of steps {FIRSTGROUP} to {LASTGROUP}; `git status`, read as the files those steps own changed and nothing else; run `node {HUB}/session-guards.test.mjs` with no switch once, in the background as the background rule says, read as every case passing, and where a case is red put it right as the Facts say and run the red cases by name once in the foreground, ending FAILED naming a case still red and the step that owns its file; before the plants run, read every plant of the guard files whose target line the edits changed and move its find; for each guard file in the order above, write the note, launch the plants narrowed to that file, write the note again as the very next call, end the turn on the run and read its output whole, and where a plant is missed or stale strengthen the case in its case file and run that file's plants once more, ending FAILED naming a plant missed a second time; the checks {CHECKS} once each, each exit code read, the lessons check in the foreground because it ends in seconds; one commit for each of steps {FIRSTGROUP} to {LASTGROUP} in that order, nothing staged beforehand, each made with `git commit -m` naming that step's files after its message, a plain message naming its finding keys; then the landing acts: {LANDING}. Observe: every case passing, every plant of the edited guard files caught, the checks exit 0, one commit with a plain message for each file step, the remote's main the pushed commit with those commits above the fetched head, a doctrine gates run for it, the clone's head equal to the remote's main, and the status clean with nothing between the tracking ref and main. Kill: a red case after its fix, a plant missed a second time or a red check ends the step FAILED with its lines and nothing pushed; a red case whose fix needs a line outside the files named for it, or whose cause cannot be read from the case and the code, ends it EJECT naming the lines, with nothing written after; a conflict in the rebase or a push refused as not a fast-forward ends it EJECT with nothing pushed and the rebase ended; a refusal of a command by a guard or by the harness's permission check ends it REFUSED with the refusal's words, nothing further done and no other route tried. Report `progress/step-{COMMIT}-report.txt` (new); a send after the first writes its own file, named for the step number, a hyphen, the send's number and -report.txt. Estimate {COMMITEST} min.
