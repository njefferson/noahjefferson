# The plan seed's standing text

The owner edits these words and `plan-seed.mjs` reads them: each block opens with a line of two at-signs and its name, and runs to the next such line. A word in curly braces is filled by the seed at the time of the print: HUB (the full path of the repository the print is for, the working copy and never the live clone), ITEM (the program key), TAKEUP, CLOSE and REVIEW (the step numbers), NEXTP (the next free program key), NEXTQ (the next free found key), NEXTL (the next free lesson number), TRANSCRIPT (the session's transcript path), REVIEWFILE (the review's full path) and PUTRIGHT (empty, or in a batch print the paragraph that sets the items of findings whose own text says they were put right to done at the take-up, each with that sentence as what changed) and LANDING (the landing block below, whole). Nothing above the first block is printed.

@@ rules-of-this-plan
- Every step runs on the sonnet tier; the main thread manages and does no step.
- The agent's first call is the Read tool on `/root/.claude/hub/agent-rules.md`, made alone, with no other call in the same turn; a first call sent beside another was refused and latched an agent on 3 November.
- Each step has four parts the agent reads before acting: Facts, what the step depends on, restated; Do, the exact actions; Observe, what must be seen for the step to be DONE; Kill, what ends the step with nothing further written. On a red check or an observation that is not the one named, the agent writes what it saw into its report, hands back FAILED naming it, and writes nothing after. An observation the step did not foresee, or a judgement the step does not settle, hands back EJECT with what was seen and the files named, and writes nothing after.
- Every report's first line after its verdict word is the wall line: one sentence answering whether the step still serves this plan's goal 1, whether that goal still serves the program's thesis, and whether what was seen moved either.
- Every file is read with Read or Grep and written with Edit or Write; each shell line is one command from Commands, with no `cd`, no variable assignment in front of it, no semicolon, no `&&`, no pipe and no redirect; git is written bare, and the shell already starts in the repository the plan names, so git and the checks run as the Commands list them with no change of directory first; the one exception is the live clone, whose lines carry git's directory flag and the clone's full path, which the plan fence reads away before matching. Every git read is bare, with commit ids and plain flags, and carries no format string and no percent code. A run that may pass ten minutes goes in the background, the agent ends its turn on it with no loop and no wait of its own, its completion resumes the agent, and its output is read from the harness's task output and written into the scratchpad file the step names with Write.
- No file quotes the owner. An event is named by its California date and time, never by an agent's or a task's id, and no run of seven or more hex-set characters is written that a command in that agent's run did not print.
- Each commit is made under the container's default git identity with a plain, reader-facing message carrying no chat link, no model's name and no trailer of any kind, whatever the harness's attribution reminder asks. Nothing is pushed except by the take-up step, which lands its one commit, and the close step, which lands the plan's other commits with its own; each fetches the remote's main, puts the commits on top of it with a rebase, and pushes main as a fast-forward, never forced; a conflict ends the rebase and the step ejects with nothing pushed.
- A send after the first of any step reads that step's report and `git status` first, does again nothing the report says landed, and starts from the list of what remains that the report gives.

@@ take-up
{TAKEUP}. **Taken up: {ITEM} set to planned with this plan's name and landed, so another session's seed skips it.** Hub, one agent. Facts: the item is {ITEM} in `PROGRAM.md`, and a seed printed by another session reads an entry whose State is open as work to take; the remote's main moves under this session, so it is fetched at the time and this step's commit goes on top of it. Do: `git status`, read clean; read `PROGRAM.md` whole; in the entry of each item the plan names, {ITEM}, set State to planned and Plan to this plan's title as written on its first line{PUTRIGHT}, and change no other field or line; after `git add`, run the checks of the Commands once each, each exit code read; make one local commit with a reader-facing subject saying the item is taken up; then the landing acts: {LANDING}. Observe: the entry reads State planned with this plan's title, the checks exit 0, the remote's main is the pushed commit with this step's commit above the fetched head, a doctrine gates run exists for it, the clone's head equals the remote's main, and the status is clean with nothing between the tracking ref and main. Kill: a red check ends the step FAILED with its lines; a conflict in the rebase or a push refused as not a fast-forward ends it EJECT with nothing pushed and the rebase ended; a refusal of the fetch, the rebase, the push or the pull by a guard or by the harness's permission check ends it REFUSED, nothing further done and no other route tried. Report `progress/step-{TAKEUP}-report.txt` (new). Estimate 15 min.

@@ review-step
{REVIEW}. **Review.** Hub, one agent per send, Standing. Follow {REVIEWFILE} by that full path for the move the manager notes' unnumbered `Next:` line names, and hand back its verdict line first. This step is never a resend: a send of it reads no step's report as its own and does none of any step's Do, and it follows the review file from its first line whatever the manager notes say was sent before. The review judges that move and does none of it: it does not carry out the Do of the step it judges, runs none of that step's commands, starts no background run, and writes nothing but its own record in the scratchpad's `progress/` folder. Every file, the repository's own files and its git configuration among them, is read with the Read or Grep tool. The only shell lines are the one `node` command on the review's script under the scratchpad and a single git read the agent rules list; its git reads are bare, `git status`, `git log`, `git show` or `git rev-parse` with commit ids and plain flags, and carry no `--format` or `--pretty` string and no percent code; each shell line is one command, with no `cd`, no variable assignment in front of it, no semicolon, no `&&` and no pipe.
